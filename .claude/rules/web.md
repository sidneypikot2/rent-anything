# Web conventions (Next.js)

Next.js 16 App Router, TypeScript (strict), Tailwind CSS 4, TanStack Query. **This Next.js is newer than your training data**: before using an API you aren't sure of, read the guide under `web/node_modules/next/dist/docs/` (`web/AGENTS.md` says the same; `next dev` rewrites that file, so leave it as it is).

**Checks**: `script/check frontend` — ESLint, `tsc` (after `next typegen`, which generates the route types such as `LayoutProps`), `next build`, and the API contract. ESLint also runs on each file you edit. None of it executes the app; `script/smoke` does (`tools/smoke/tests/`). It finds elements by `data-testid`: renaming one means updating the test in the same change. Run npm commands through the scripts or `docker compose run --rm web ...` so the lockfile is resolved in the same Node as CI.
Google sign-in works only on port 8100, the one origin registered on the OAuth client: in a worktree (8100+N) Google answers 403, so test it on the main stack; the smoke test ignores those 403s.

**API access**: only through `apiClient()` in `web/src/api/client.ts` (openapi-fetch, typed from `src/api/schema.d.ts`), or, in a Server Component calling a public endpoint, `serverApiClient()` in `web/src/api/server-client.ts` — `apiClient()` imports the browser-only auth session and breaks the server build. Server fetchers call `connection()` first (`src/api/discovery.ts`) so `next build` doesn't prerender against the API. Never `fetch` the API directly, and never edit `schema.d.ts` — change the backend's request spec and run `script/check-api --write`. Where the API is comes from `web/src/lib/config.ts`: server code uses `API_INTERNAL_URL` (inside Docker the backend is `http://backend:3000`), the browser derives it from its own port (8100+N → 3100+N).

**Server vs client**: public browse pages (`/[area]`, `/[area]/[category]`, `/listings/[id]`) are Server Components that fetch on the server, for SEO and fast first paint. Signed-in pages (cart, bookings, partner dashboard, admin) are Client Components using TanStack Query (provider in `src/app/providers.tsx`). Mark a file `"use client"` only where it needs state, effects or browser APIs, and keep server-only values (anything without `NEXT_PUBLIC_`) out of client files.

**Three sections**: guest pages are in the `src/app/(guest)/` route group, partner pages under `src/app/partner/`, admin pages under `src/app/admin/`, each with its own layout and `SectionHeader` (`src/components/landing/`). A sign-up on `/register` makes a guest and one on `/partner/register` a partner; `/admin` has no sign-up. Every other `/partner` page is partner-only (`auth.md`). Area pages are `/[area]` at the top level, so an area slug can never be a top-level route: `Area::RESERVED_SLUGS` (`partner`, `admin`, `search`, `login`, `register`, `dashboard`, `profile`, `settings`, `nearby`, `cart`, `trips`, `listings`) — a new top-level guest route goes on that list too.

**Area first**: every traveller-facing page lives under an area (`/bantayan-island/...`), and the selected area and trip dates travel in the URL. The cart is a list of the guest's trips, which can span areas (`.claude/rules/trips.md`). A destination page's trip dates and guests are `?from=&to=&guests=` (`readTripDates` in `src/components/trips/trip-dates.ts`, which drops past or broken values).

**Add to trip** (RAA-66, `src/components/trips/`): `TripAddProvider` runs the flow for the listings inside it. Signed out, there is no sign-in first (RAA-177): the add makes a guest with no account (`startGuestSession`, `POST /guest_sessions`) and carries on; checkout asks who they are (below). With no current trips (`deletes_on` null) the add creates one; otherwise the which-trip sheet asks, preselecting `GET /trips/suggestion`. On a place's page (`TripAddProvider places`) the sheet never asks: the add goes to the trip its banner shows (`tripHere` in `use-trip-here.ts`: the chosen one, else one with something here), or starts a new one, which becomes the chosen trip — so an add can't land in, or switch the page to, another trip; the sheet then asks only dates, guests and a new trip's name. Which trip to suggest, trip names and date extension are the server's — don't compute them in the browser.

**Cart and Trips page** (RAA-68, RAA-135): `/cart` sits on a white sheet (`PageSheet tone="paper"`, cards with `edge="line"`) in two columns from `lg` — the trips from `GET /trips` in a sticky list (`CartTripNav`; on a phone a Switch trip button in the trip's header opens them in a sheet, `TripSwitchSheet`, RAA-161) beside the one picked (`TripDetails`: a forest header, then its items as cards) — with the fix-ups (move, re-date, remove an item; rename, merge, delete a trip). `?trip=<id>` picks the trip (the toast's View trip); picking another rewrites it with `history.replaceState`. An item card's title opens `CartItemPanel` (`Dialog placement="side"`): its booking from `GET /bookings/{id}` (status, dates, guests, total, answer-by time, history) over `ListingPanel` — never a link away to the destination page. `/trips` (RAA-140) has the same layout for trips with a booking (`GET /trips?view=booked`), behind an Upcoming | Past | Cancelled switch over the sidebar (Happening now and Upcoming, or Past, by `trip-phase.ts`; the sidebar lists trips only), through `TripDetails mode="trips"`: only the booked items, Day by day at first, no ticks or edits, a past booking's panel offers Book again (the `TripAddProvider` flow). Any trip can be planned again (`RecreateTripSheet`, `POST /trips/{id}/copy`), landing in the cart. Cancelled lists, with no sidebar, the bookings no trip holds any more (`CancelledBookings`: cancelled, declined, expired — such a booking lets its item go; a completed one stays in its trip). In the cart, Find more (`FindMoreSheet`) links out to the trip's destinations and to `/search`, carrying its dates and guests, where the usual add flow suggests the trip — it never adds from the cart itself. Prices, problems (dates taken, listing off) and totals come from `GET /trips/{id}/quote` (`useTripQuote`): an item with a problem can't be ticked, and the browser never prices anything itself. A trip whose items are in more than one place lists them under a heading per place (`byPlace` in `trip-details.tsx`, by each item's `destination` from the API), in the order the trip reaches them. Under the trip's header, "Still needed" lists the trip's nights still ahead with no stay or too few beds (`missingStays` in `trip-missing.ts`), each with Find a stay to the place the trip is in just before them (`#need-stay`, with the trip's dates): a hint, it never stops checkout. Items | Day by day switches to `TripItinerary` (`itinerary.ts`), which flags two stays on one night and empty days. The cart shows `DeletionBanner` while `deletes_on` is set. The header badge counts items in current trips, not trips. An item's `booking_type` decides one day or a range (`RANGE_TYPES` in `format.ts`).

**Booking** (RAA-133, `src/components/bookings/`): in the cart every item that can be booked (`bookable`: dated, not past, no booking holding its days) is ticked at first, and the trip's foot books the ticked ones in `CheckoutSheet` — "Book" for instant-book listings, "Send requests" for request-to-book ones, "Book and request" for both (`checkoutLabel`). One idempotency key per sheet, so a retry can't book twice; the API prices and checks everything again, all or nothing, and its refusals name the item. A booked item shows `BookingStatusBadge` in place of its tick, and its menu only opens its panel: moving, re-dating and removing are the API's to refuse, and the menu doesn't offer them. From the panel a booking that hasn't started can be edited (`ChangeBookingSheet`, `PATCH /bookings/{id}`: it goes back to the partner as a request) or cancelled (`CancelDialog`, in the cart and on `/trips`, showing `refund_if_cancelled_cents` from the API — never work a refund out in the browser). There is no bookings page: bookings show with their trips, and cancelled ones under Cancelled on `/trips` (a top-level `/bookings` would need `Area::RESERVED_SLUGS`). `InstantBookBadge` (`src/components/discovery/`) marks an instant-book listing wherever a guest sees one (rows, cards, the side panel, map pop-ups, the listing page) and in the partner's listings table. Every listing is request to book since RAA-134, so a checkout comes back as requests that wait for their partner. **Paying** (RAA-143): an accepted request is `awaiting_payment` until its pay-by time (`expires_at` on the item's `booking`); in the cart it is ticked like an item to send, on its own selection, and a second foot pays for the ticked ones in `PaySheet` (`POST /bookings/pay`, all or nothing), which confirms them; the item panel has a Pay button for one. The cart's Items view lists a trip's items by place (`byPlace`, above), never by where their booking stands: each card shows its own status, and the send and pay feet sit together under the items (sticky from `lg`), each hidden while it has nothing to do (RAA-152). Day by day has neither foot: sending and paying happen in Items. Until payments are live both sheets say nothing is charged. **Without an account** (RAA-177, `src/components/guest/`): a guest with no email yet (`isAnonymous`) gives name, email and phone in `CheckoutSheet` (`contact`); an email another guest has comes back 409 (`CodeRequiredError`), the sheet asks for the emailed code (`CodeForm`), and once signed in with it (the API moves the trips over) sends again. The first checkout's `trip_link` shows once in `TripLinkCard`, and the session's user is read again (`refreshSessionUser`). `/trips/open/[token]` (`TripLinkUnlock`) asks for the PIN on every open and keeps the session in this tab only (`saveSession(…, { tabOnly: true })`, sessionStorage, which wins over localStorage while it is there); its recovery and `/login/code` sign in with an emailed code (`EmailCodeForm`). `CartAccountBar` over the cart offers sign-in to an anonymous guest, and to one with an email `/trips/keep` (`KeepTrips`, `POST /me/register`) and Reset trip link and PIN (`POST /trip_access/rotate`). An anonymous guest counts as signed out in the header and on `/login`.

**Admin console** (RAA-142, `src/components/admin/`): `/admin` signs the team in and sends them to `/admin/bookings`, whose tabs are `AdminNav` in the header. Booking requests lists `GET /admin/bookings` by status (requests soonest to expire first) one line per booking (listing and type, business, traveller, dates, total); a click on a row opens its complete details (both people's contacts, money, notes, times) in `Dialog placement="overlay"`. An accepted request waits under Awaiting payment, with its pay-by time, until the guest pays (RAA-143). It answers a request on its partner's behalf (Accept; Decline through a `Dialog` with an optional reason). Partners can still answer their own in the partner calendar, so an answer can come back refused as already given. Export CSV downloads the chip's list as it is on screen (`bookings-csv.ts`, built in the browser, so at most the API's 200 rows). **Destinations** (RAA-166, over RAA-164's API): `/admin/destinations` lists every area, drafts included (`GET /admin/areas`: search by name, slug or alias, status and kind filters, 50 a page); `/admin/destinations/new` and `/admin/destinations/[slug]` are one form (`destination-form.tsx`) — a change sends only the fields that differ (the API keeps the rest), and a new area gets its banner photo once saved. The banner uploads like a listing photo (`useAreaBanner` in `use-admin-areas.ts`, `web-photos.md`); the boundary and the Wikidata names and popularity are the gazetteer's, shown read-only. **Places to see** (landmarks, same tickets) work the same way at `/admin/landmarks` (`landmarks-list.tsx`, `landmark-form.tsx`, sharing the destination form's aliases field and the tags from `GET /admin/area_options`): no delete (back to draft hides one), and the destination is never picked — the API takes it from the pin, as for a listing.

**Partner calendar** (RAA-120, `src/components/partner/calendar/`): `/partner/calendar` is one grid of every listing's days. `usePartnerCalendar` loads `GET /partner/calendar` in windows (the API serves at most 92 days) with `useInfiniteQuery`, paging both ways as either edge scrolls near, and merges them per listing; the grid opens with today in view and keeps its scroll position when earlier days are put in front. It renders the Ledger's days as they come — price, units left, blocks — and never counts availability itself (`bookings.md`). A pending booking (`isPendingBooking`: a request or an unpaid hold) holds its days like a confirmed one but draws as a dashed aqua bar; its sheet answers a request (Accept, Decline) and cancels anything else not yet under way. `capacity_unit` says what a row counts: a joiner tour (`seats`) fills seat by seat, shown as "n/N joined" and open until full, with no booking bars. A stay's selected days are nights, so an offline booking's check-out is the day after the last one. Drag across a row with a mouse; touch and keyboard pick the first day, then the last.

**Layout**: mobile-first — most travellers book from a phone. Check every page at phone width.

**No `:target` styling**: client navigation (a Next `Link`, `router.push`) never updates `:target`, so a `target:` style only shows on a full page load (RAA-78). Highlight from `location.hash` in a client effect, or just let the anchor scroll.

**Session-dependent UI above the fold**: the session is read from localStorage after hydration, so server-render the signed-out/traveller version and swap it once `useSession()` resolves. Rendering nothing until then is only fine below the fold, and even there hold the space (`PlanCta` renders the signed-out band `invisible`) so the page doesn't grow — above it, the main call to action is missing from the first paint (RAA-80).

**One-shot URL flags** (like `?start=trip`): read them once into client state and drop them with `history.replaceState`. sign-in returns to `pathname + search` (`?next=`), and `TripDatesBar` rebuilds the query from scratch, so a flag left in the URL either comes back after sign-in or vanishes when dates are set (RAA-80).
