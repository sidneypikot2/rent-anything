# Auth and roles (RAA-23)

**One `users` table, role fixed by the entry point.** `role` is `guest`, `partner` or `admin` (CHECK constraint). The client sends the role of the page it is on (`/login` and `/register` → `guest`, `/partner/login` and `/partner/register` → `partner`, `/admin` → `admin`), never one the user picks. Sign-up and Google/Facebook accept only `guest` and `partner` (`User::SELF_SERVE_ROLES`); admins are never self-made. `bin/rails admin:grant EMAIL=… [PASSWORD=…]` (`Auth::GrantAdmin`, RAA-141) makes one as a separate user with the same email — not a role change, which the composite foreign keys to `users (id, role)` (profiles, OAuth identities, listings) refuse for anyone who has them.

**Email is unique per role** (RAA-29): unique `(email, role)`, and the validation is scoped to `role`. One person can have a guest account and a partner account with the same address, each with its own password, and they are separate users. Every sign-in looks up `(email, role)` for the page's role, so on another role's page that account just isn't found: a 401, never a 403, and never converted. Anything that finds a user by email must also scope it to a role.

**Tokens**: every sign-in returns `Auth::IssueTokens` — a 15-minute JWT access token (`sub`, `role`) and a 30-day refresh token stored only as a SHA-256 digest. `POST /api/v1/tokens/refresh` rotates it; presenting a token spent more than a minute ago revokes all of that user's sessions (within the minute it is two tabs refreshing at once, and the browser picks up the other tab's new session). Don't raise inside the refresh transaction — the revocation would roll back with it. **The refresh cookie** (RAA-306, `RefreshCookie` in `app/controllers/concerns/refresh_cookie.rb`): a request with `X-Refresh-Cookie: 1` (the web app) gets the refresh token as the HttpOnly `raa_refresh` cookie (host-only on the API, `Path=/api/v1`, `SameSite=Strict`, `Secure` outside development and test, expiring with the token) and none in the body, and refresh and sign-out read a body token when one is sent (a session from before the cookie, which moves into it), else the cookie (sign-out with neither is a 204); in that mode an `Origin` other than `FRONTEND_ORIGIN` is a 403, and CORS allows credentials. Without the header the token stays in the body: native apps and a trip link's tab-only session, which must never send it (the cookie is the browser's, so it would replace that session). Specs document it with `refresh_cookie_header` (`spec/support/refresh_cookie_docs.rb`). Every controller that issues tokens includes the concern and renders with `render_tokens`; a new way to sign in does too. Sign-out and account deletion delete the cookie only in cookie mode, so a trip-link tab signing out leaves the browser's own session.

**Endpoints that need a user**: `before_action :authenticate_user!` (401), then `require_role!("partner")` (403) — or scope through `current_user`. Everything under `/api/v1/partner` is partner-only; its request specs cover signed out (401) and a guest (403).

**Rate limit**: endpoints that sign in or sign up call `limit_auth_attempts only: :create` (`ApplicationController`, Rails `rate_limit`, `AUTH_RATE_LIMIT` per IP per endpoint), which answers 429 with the `error` schema and `Retry-After`. Every limit is a named constant there (RAA-219: `REFRESH_RATE_LIMIT`, `WEBHOOK_RATE_LIMIT`, `BROWSE_RATE_LIMIT` for search, explore and quotes, `SIGN_IN_PER_EMAIL_LIMIT` on password sign-in) applied with `limit_requests`; `limit_browsing` leaves out private addresses, the web app's own server rendering pages over `API_INTERNAL_URL`, so a public endpoint that server calls uses it, not a plain per-IP limit. The test cache is a null store, so specs use `exceed_auth_rate_limit(Controller)` or `exceed_rate_limit(Controller, LIMIT, name:)`, and `from_public_ip` for a browsing limit.

**Guests without an account** (RAA-175): `POST /guest_sessions` makes a guest with a null email (a CHECK allows it only for a guest whose profile isn't complete; `User#anonymous?`), who gives name, email and phone at their first checkout (`Guests::ClaimContact`; an email another guest has is a 409 `CodeRequiredError` plus an emailed code, and `POST /sign_in_codes/verify` from the emailless guest moves their trips over, `Guests::Absorb`). Sign-in, sign-up and OAuth do the same: their controllers read the optional bearer (`authenticate_user`) and pass `current_user:` to the service, and `Absorb` only ever moves trips into a guest. A new way to sign in must do it too. Code that reads `user.email` must allow nil. They come back through their trip link and PIN (`TripAccess`, `Auth::UnlockTripLink`): its session's refresh token has `fixed_expiry`, so `Auth::Refresh` keeps its first `expires_at` — any new way of issuing tokens must pass `session_ends_at` through the same way. Emailed one-time codes (`SignInCode`, HMAC-digested) recover a lost link or PIN; asking for one always answers 202. `registered` (password or OAuth) is what keeps their trips from `Guests::Purge`; `POST /me/register` sets a password.

**Email confirmation and password reset** (RAA-214): `users.email_confirmed_at`; the links are `generates_token_for` tokens on `User` (no table): `email_confirmation` (24 hours, embeds the email, so a changed email spends it) and `password_reset` (30 minutes, embeds the password salt, so it works once; `has_secure_password reset_token: false` drops Rails' own). `AccountMailer` sends both to the web app's `/confirm-email?token=` and `/reset-password?token=`. Sign-up with a password and `POST /me/register` email the link (`Auth::SendEmailConfirmation`; `POST /email_confirmation` again, signed in); `POST /email_confirmation/verify` needs no sign-in. `POST /password_reset` (email and the page's role) always answers 202 and mails only an account with a password; `PATCH /password_reset` (`Auth::ResetPassword`) revokes every refresh token and confirms the email. An emailed sign-in code confirms it for an account without a password (the code proves the inbox, not who set a password), and Google's `email_verified` does too; Facebook's never does. The emails ask the reader to confirm only an account they made. A password account with an unconfirmed email (`User#email_confirmation_required?`) gets a 403 with `code: "email_unconfirmed"` (`EmailUnconfirmedError`) from `Checkouts::Create` and `Payments::Pay`; a guest without a password, who gave their email at checkout, isn't held up. Sign-in stays allowed. A new way to take money from a guest checks it too. The migration marked every account that then had a password or an OAuth sign-in as confirmed (staging only, no production yet), so on old rows `email_confirmed_at` is not proof of ownership.
**Deleting an account**: a guest deletes their own from Settings (`DELETE /me`, `Users::DeleteAccount`, confirmed by typing DELETE in `DeleteAccount`, `web/src/components/account/delete-account.tsx`). What goes with a user is listed once, in `Users::Erase`, which `Guests::Purge` uses too: trips with their items, OAuth identities, refresh tokens (every device signs out), the profile, the user; trip access and sign-in codes cascade. Bookings, checkouts, payments and booking events stay for the partner, with `user_id` nulled and the booking's own copy of the guest's name, email and phone. Refused with a 409 (`OpenBookingsError`) while any booking is open (`Booking::UNSETTLED`). Partners and admins get a 403: a partner emails `SUPPORT_EMAIL` (`web/src/lib/brand.ts`, shown in partner Settings) and the team closes the account. A new table holding a user's data either goes in `Users::Erase` or keeps its rows with `user_id` nulled, never blocks the delete.

**Complete profile** (RAA-32): sign-up takes only email and password, and a Google/Facebook account has no phone, so every new guest or partner starts with `users.registration_complete = false` and a possibly null `name`. `PUT /api/v1/me/complete_profile` (`Users::CompleteProfile`) requires both `name` and `phone` and sets the flag; from then on the model and a CHECK constraint keep both present. The web app doesn't call it or route on the flag yet, so anything showing a user's name falls back to the email. A phone, whenever it is saved, must be a phone number (`User` validation).

**Profile**: `PATCH /api/v1/me` (`Users::UpdateProfile`) changes `name` and `phone` only — email and password changes need verification and a current-password check first. Once the profile is complete, neither can be cleared. Each role's profile is separate (RAA-40), because guests and partners will need different fields: `GET`/`PUT /api/v1/partner/profile` (`Partners::UpdateProfile`, table `partner_profiles`, plus an optional `display_name`; travellers see a listing's business name instead — a partner runs one or more businesses (`/api/v1/partner/businesses`, RAA-100) and needs one to add a listing (403)) and, for guests only, `GET`/`PUT /api/v1/me/profile` (`Guests::UpdateProfile`, table `guest_profiles`). What they share lives in one place — `Profiles::Update` (legal first and last name, phone saved on the user, a full address with an optional province) and the `ProfileAddress` model concern — so a rule both need changes there; a field only one needs goes in that one's service (`own_attributes`) and table. `complete` is true once the profile is saved with a phone.

**OAuth** is verified server-side only: `Auth::Providers::Google` (ID token, audience `GOOGLE_CLIENT_ID`) and `Auth::Providers::Facebook` (`debug_token` against `FACEBOOK_APP_ID`, then `/me` with `appsecret_proof`). Identities are per role too. `oauth_identities.role` is unique with `(provider, uid, role)` and kept equal to the user's by a composite FK to `users (id, role)`. So the same Google account on `/login` uses or creates the guest account, and on `/partner/login` the partner account. Within the page's role, a provider login links to an existing account by email only when the provider vouches for the email (Google's `email_verified`) **and** that account has no password — email sign-ups don't prove they own the address, so linking one would hand the real owner's Google login to whoever registered it first. Facebook's email never links. Proper email verification (M1) can relax this. Specs stub `Auth::Providers::*.verify`; nothing calls Google or Facebook from a spec.

**Web**: the session (tokens + user) is in localStorage via `src/lib/auth/session.ts`; `useSession()` is `undefined` until hydration — wait it out before redirecting. `apiClient()` adds the bearer token in the browser and refreshes once on a 401 GET; `bareApiClient()` (no middleware) is only for that refresh. Signing in lands on the role's dashboard (`DASHBOARD_PATHS` in `src/lib/auth/paths.ts`: `/dashboard`, `/partner/dashboard`, `/admin/dashboard`), or on `?next=` when `/login` or `/register` has one: always through `safeNextPath`, which takes only a path on this site (an open redirect otherwise). `AuthCard`'s `onSignedIn` skips the redirect for a card in a sheet over the page. A guest with no account yet (`isAnonymous`, RAA-177) is signed out to the header and `AuthCard`; a trip link's session is `tabOnly` (sessionStorage), and signing out (`clearSession({ all: true })`) ends both. The header's signed-out Sign in / Create an account links are hidden on `/login` and `/register`; signed in, guests and partners get an account menu (`AccountMenu`: Profile, Settings, Sign out — `/profile`, `/settings` or `/partner/profile`, `/partner/settings`; partners also get Add business, `/partner/businesses/new`; a guest without a password gets Keep your trips, `/trips/keep`, in place of Settings, and in a trip link's tab-only session Sign out reads Close trips and goes home, RAA-179), admins their name and Sign out. Signed-in guest pages go in `src/app/(guest)/(signed-in)/`, partner pages in `src/app/partner/(protected)/` and admin console pages in `src/app/admin/(console)/` (RAA-142; `/admin` itself is the sign-in, `/admin/ui-kit` stays open), all behind `RoleGuard`; only `/partner/login`, `/partner/register` (and `/partner`, a redirect) sit outside the partner group. Sign-in and sign-up are separate routes (`LOGIN_PATHS`, `REGISTER_PATHS`); `AuthCard` takes its `mode` from the page, it doesn't toggle. Guest `/login` and `/register` are `AuthCard plain` in `AuthSheet` (RAA-253), one white sheet on the right of the backdrop (across the width on a phone), 12px under the header at every width like the home hero, so going from `/` to sign in leaves the frame in place, with a `BannerCarousel fade` from `lg` running from the header's left edge 32px in under it (`AuthCarousel`, mounted only at that width so a phone never loads the photos). From `lg` the two are one frame, which owns `card-edge` and the shadow and clips both, so the sheet's left corners are a clean curve on the photo, as tall as the hero (`AUTH_FRAME_HEIGHT`), `compact` fields and Google and Facebook in equal columns (`OauthButtons inline`, stacked below `sm`; the form is 27rem so each column clears the 186px Google needs). The whole sheet fits the first screen on load, down to 1366×650 and 375×667, with the site footer below it; check both sizes when adding to the form. Google and Facebook sit under the form on both pages, as on sign-up they wait on its consent tick, and the sheet ends with a link to `/partner/login` — not `/partner`, which sends a guest with a session, even one with no account, to `/dashboard`. `/partner/login` and `/partner/register` take the same place and height on one white frame (`PartnerAuthFrame`, the pitch beside `AuthCard plain` from `lg` and under it below that, never the carousel), which also fits the first screen, so `PageSheet` is the `(protected)` layout's, not the partner layout's. **Consent**: sign-up (guest and partner) and checkout without an account carry a required `ConsentField` (`src/components/legal/consent-field.tsx`: the Terms and Privacy policy, plus the Partner terms for a partner); on sign-up Google and Facebook stay disabled until it is ticked, and a sign-in page, where they can also make an account, shows `ConsentNote` under them. A new way to make an account or hand us someone's details carries it too. The API records it: `POST /registrations`, `POST /oauth/{provider}` when it makes a new account, and a checkout's `contact` take `terms_accepted: true` (else 422, `User::TERMS_REQUIRED`) and set `users.terms_accepted_at` and `terms_version` (`User::TERMS_VERSION`, the policies' date: bump it when they change; `User.terms_acceptance`). Signing in to or linking an existing account doesn't ask again. Accounts from before it have both null. The guard is UX — the API's 401/403 is the real check.
