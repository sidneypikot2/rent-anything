# Listing photos (RAA-106)

**Storage**: Cloudflare R2 through its S3 API, with no Active Storage (the engine is off in `config/application.rb`). `PhotoStorage` (`app/services/photo_storage.rb`, `aws-sdk-s3`) is the only code that talks to the bucket: signed upload URLs, `exist?`, download, upload, delete and public URLs. Keep `request_checksum_calculation` / `response_checksum_validation: "when_required"` on its client. Without them R2 refuses our own uploads (the sizes), because the SDK adds a CRC32 next to Content-MD5; only a real bucket shows this. Every hosted environment uses the same bucket (`render.yaml`). A local stack uses it too when `backend/.env` has the `R2_*` values (`backend/.env.example`). With `R2_BUCKET` left blank, development keeps photos on disk instead (`PhotoStorage.disk?` → `PhotoStorage::Disk`, `backend/public/dev-photos/<key>`, gitignored). Rails serves those files from `public/`, and the browser uploads to `PUT /dev/photo_uploads/:token` (`Dev::PhotoUploadsController`), which is routed only in development and test and is not part of the API contract. That endpoint checks the signed key, type, size and MD5 as R2 would, so the web app's code is the same for both. `DEV_BACKEND_URL` (`docker-compose.yml`) is the backend address the browser uses for both. The bucket's CORS policy (set in the Cloudflare dashboard, not in the repo) must allow `PUT` from every web origin that uploads (staging's and `http://localhost:81xx`), with the `Content-Type` and `Content-MD5` headers (what `upload.headers` holds). libvips is in `backend/Dockerfile` for the sizes, and in the `test` job of `.github/workflows/ci.yml`, which runs specs on the host Ruby: change both together.

**Destination and place photos** (RAA-210, over RAA-164's one banner): an area's and a landmark's photos (`AreaPhoto`, `LandmarkPhoto`, set by the team in the admin console) work the same way, up to `GalleryPhotos::MAX` (12) each, numbered by `position` like a listing's; the first ready one is the area's banner or the landmark's card photo. `GalleryPhotos::Create` adds one after the others under a lock on its owner; `GalleryPhotos::Update` confirms it (`ListingPhotos::Update`) and/or moves it (`position`, the others shifting), so replacing a photo is add, move into the old one's place, delete; `GalleryPhotos::Destroy` closes the gap. Admin routes: `admin/areas/:area_slug/photos` and `admin/landmarks/:landmark_slug/photos`. `StoredPhoto` (model concern) holds the key, the validations and the file cleanup all three models share, and `PhotoUploadValues` (service concern) the checks on what the browser declares. `ResizeJob`, `DeleteFilesJob`, `PurgeUnfinishedJob` and `ListingPhotos::Update` take any of them. Guests get both in `GET /areas/:slug` (`Discovery::AreaDetail`: `photos`, and each landmark's). The `banner_photo` route and field (`AreaBannerPhotosController`) are deprecated aliases for the first photo, kept only until the admin console uses the photos (RAA-211); delete them after that.

**Keys**: a file's key is `<root>/<table>/<id>/<field>.<extension>`, built from the row and never stored, with `image_card` and `image_large` next to `image` (`ListingPhoto#key`). Any future model with files follows the same convention and uses `PhotoStorage.root`. The root is the environment's name: staging's keys start with "staging". Changing an environment's name moves its photos: RAA-172 renamed staging's env from `production`, so its files were copied from "production/" to "staging/" first. In development it is also the local stack's folder, e.g. development/sidney-rent-anything/listing_photos/12/image.jpg. `docker-compose.yml` sets it as `DEV_STORAGE_FOLDER` from the developer (`$USER`) and the Compose project, which `script/worktree-env` makes unique per worktree. Without it, every local database, each numbering its photos from 1, would write over and delete the others' files. A development process outside Compose gets "unnamed".

**Upload**: the browser never sends a file to this API, and a listing exists before its photos (it starts as a draft). `POST /api/v1/partner/listings/:listing_id/photos` (`ListingPhotos::Create`) checks the type (JPEG, PNG, WebP), the size (≤ 10 MB), the MD5 and the photo limit (`Listing#photo_limit`: 12, or 5 for a tour, RAA-110). It adds the row after the listing's others, under a lock on the listing, and returns a URL signed for exactly that key, type, size and MD5. The browser `PUT`s the bytes there, then confirms with `PATCH .../photos/:id` `{uploaded: true}` (`ListingPhotos::Update`). The confirm checks that the file is in storage, sets `uploaded_at` and enqueues `ListingPhotos::ResizeJob`; sending it again is harmless. The job re-saves the original over itself without its metadata, turned upright (a phone photo's EXIF can hold the GPS point of a partner's home, which guests learn only after a paid booking). It then makes both sizes from that copy and sets `sized_at`. Keep the original stripped before anything is shown to guests, and never serve an unstripped file. The raw upload sits in the public bucket only for the seconds before the job runs, at an id no one has been shown. Photos never confirmed are deleted after two days (`ListingPhotos::PurgeUnfinishedJob`, daily). Deleting a photo, or its listing (one photo at a time, `dependent: :destroy`), enqueues `ListingPhotos::DeleteFilesJob` for all three keys after commit. The foreign key's cascade alone would leave the files behind.

**Sample photos** (RAA-115): the sample partners' (`@example.com`) live listings get a photo from `backend/db/sample_photos/` (Unsplash stand-ins, copies of the web app's `public/images/samples/`) through the same services as a partner's upload: `ListingPhotos::Create`, the file written at its key, `ListingPhotos::Update`, `ResizeJob`. `CompleteSampleListings` does it (a migration for existing databases, called again from `db/seeds.rb`), and gives those partners an approved ID check so `Create` accepts them. Add a sample photo the same way, never as a row written by hand.

**Order**: `position` numbers a listing's photos. `photos` in a listing body is the full ordered list of its photo ids, and `Listings::ListingValues#save_photos!` renumbers them and destroys those left out. The `(listing_id, position)` unique constraint is deferred, so a reorder can swap positions inside one transaction. In a spec, `SET CONSTRAINTS ... IMMEDIATE` shows what a commit would do.

**Serving**: guests load photos straight from `R2_PUBLIC_URL` + the key, never through this API: it would put every image request on the staging instance. `ListingPhotoSerializer` builds every URL. Guests see only ready photos (`sized_at` set: `Listing#ready_photos`; `cover_photo` is the first of them). The partner sees all of them with `uploaded` and `ready`, and until a photo is ready both of its URLs point at the original. Preload `cover_photo`, `ready_photos` or `photos`, or each listing (or landmark) costs a query.

**Specs**: `spec/support/photo_helpers.rb` gives every example a stubbed S3 client, so nothing reaches R2. `stub_photo_in_storage` / `stub_photo_missing` set what `head_object` and `get_object` answer, and `storage_requests(:put_object)` lists the calls made. `create_photo(listing, uploaded: …)` makes a row as an upload leaves it. Keys in specs start with "test". rswag's `run_test!` submits the request in a `before` hook that every example in its `response` block shares, so check a second request inside the `run_test!` block, not in a separate `it`. The test queue adapter keeps jobs across examples, so count jobs with the block form (`expect { ... }.to have_enqueued_job`).
