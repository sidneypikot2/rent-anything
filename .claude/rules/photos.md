# Listing photos (RAA-106)

**Storage**: Cloudflare R2 through its S3 API, with no Active Storage (the engine is off in `config/application.rb`). `PhotoStorage` (`app/services/photo_storage.rb`, `aws-sdk-s3`) is the only code that talks to the bucket: signed upload URLs, `exist?`, download, upload, delete and public URLs. Keep `request_checksum_calculation` / `response_checksum_validation: "when_required"` on its client. Without them R2 refuses our own uploads (the sizes), because the SDK adds a CRC32 next to Content-MD5; only a real bucket shows this. Every hosted environment uses the same bucket (`render.yaml`). A local stack uses it too when `backend/.env` has the `R2_*` values (`backend/.env.example`). With `R2_BUCKET` left blank, development keeps photos on disk instead (`PhotoStorage.disk?` → `PhotoStorage::Disk`, `backend/public/dev-photos/<key>`, gitignored). Rails serves those files from `public/`, and the browser uploads to `PUT /dev/photo_uploads/:token` (`Dev::PhotoUploadsController`), which is routed only in development and test and is not part of the API contract. That endpoint checks the signed key, type, size and MD5 as R2 would, so the web app's code is the same for both. `DEV_BACKEND_URL` (`docker-compose.yml`) is the backend address the browser uses for both. The bucket's CORS policy (set in the Cloudflare dashboard, not in the repo) must allow `PUT` from every web origin that uploads (staging's and `http://localhost:81xx`), with the `Content-Type` and `Content-MD5` headers (what `upload.headers` holds). libvips is in `backend/Dockerfile` for the sizes, and in the `test` job of `.github/workflows/ci.yml`, which runs specs on the host Ruby: change both together.

**Keys**: a file's key is `<root>/<table>/<id>/<field>.<extension>`, built from the row and never stored, with `image_card` and `image_large` next to `image` (`ListingPhoto#key`). Any future model with files follows the same convention and uses `PhotoStorage.root`. The root is the environment's name: staging runs `RAILS_ENV=production`, so its keys start with "production". In development it is also the local stack's folder, e.g. development/sidney-rent-anything/listing_photos/12/image.jpg. `docker-compose.yml` sets it as `DEV_STORAGE_FOLDER` from the developer (`$USER`) and the Compose project, which `script/worktree-env` makes unique per worktree. Without it, every local database, each numbering its photos from 1, would write over and delete the others' files. A development process outside Compose gets "unnamed".

**Upload**: the browser never sends a file to this API, and a listing exists before its photos (it starts as a draft). `POST /api/v1/partner/listings/:listing_id/photos` (`ListingPhotos::Create`) checks the type (JPEG, PNG, WebP), the size (≤ 10 MB), the MD5 and the 12-photo limit. It adds the row after the listing's others, under a lock on the listing, and returns a URL signed for exactly that key, type, size and MD5. The browser `PUT`s the bytes there, then confirms with `PATCH .../photos/:id` `{uploaded: true}` (`ListingPhotos::Update`). The confirm checks that the file is in storage, sets `uploaded_at` and enqueues `ListingPhotos::ResizeJob`; sending it again is harmless. The job re-saves the original over itself without its metadata, turned upright (a phone photo's EXIF can hold the GPS point of a partner's home, which guests learn only after a paid booking). It then makes both sizes from that copy and sets `sized_at`. Keep the original stripped before anything is shown to guests, and never serve an unstripped file. The raw upload sits in the public bucket only for the seconds before the job runs, at an id no one has been shown. Photos never confirmed are deleted after two days (`ListingPhotos::PurgeUnfinishedJob`, daily). Deleting a photo, or its listing (one photo at a time, `dependent: :destroy`), enqueues `ListingPhotos::DeleteFilesJob` for all three keys after commit. The foreign key's cascade alone would leave the files behind.

**Order**: `position` numbers a listing's photos. `photos` in a listing body is the full ordered list of its photo ids, and `Listings::ListingValues#save_photos!` renumbers them and destroys those left out. The `(listing_id, position)` unique constraint is deferred, so a reorder can swap positions inside one transaction. In a spec, `SET CONSTRAINTS ... IMMEDIATE` shows what a commit would do.

**Serving**: guests load photos straight from `R2_PUBLIC_URL` + the key, never through this API: on the free tier every image request would wake Render. `ListingPhotoSerializer` builds every URL. Guests see only ready photos (`sized_at` set: `Listing#ready_photos`; `cover_photo` is the first of them). The partner sees all of them with `uploaded` and `ready`, and until a photo is ready both of its URLs point at the original. Preload `cover_photo`, `ready_photos` or `photos`, or each listing costs a query.

**Specs**: `spec/support/photo_helpers.rb` gives every example a stubbed S3 client, so nothing reaches R2. `stub_photo_in_storage` / `stub_photo_missing` set what `head_object` and `get_object` answer, and `storage_requests(:put_object)` lists the calls made. `create_photo(listing, uploaded: …)` makes a row as an upload leaves it. Keys in specs start with "test". rswag's `run_test!` submits the request in a `before` hook that every example in its `response` block shares, so check a second request inside the `run_test!` block, not in a separate `it`. The test queue adapter keeps jobs across examples, so count jobs with the block form (`expect { ... }.to have_enqueued_job`).
